# 개념: 설계는 워크스페이스에서, 배포는 LMS로

## 출발점

교수자는 실제로 LMS 밖에서 과정을 설계합니다. 한글 파일, 노트, 슬라이드에 목표와 주차 계획을 쓰고, 마지막에 Moodle 화면에서 하나씩 옮겨 넣습니다. LMS는 운영에는 좋지만 설계 도구로는 불편하고, 한번 옮기고 나면 원래 설계와 LMS 안의 실제 모습이 따로 놉니다.

CourseSpec은 이 현실을 구조로 만든 것입니다. **설계의 원본(source of truth)은 교수자 워크스페이스에 두고, LMS는 배포 대상으로 본다.** 소프트웨어의 "코드는 Git에, 배포는 서버로"와 같은 분리입니다.

## 세 층

| 층 | 하는 일 | 이 저장소 |
|---|---|---|
| 설계 워크스페이스 | 교수자 자료(지식베이스), 설계 에이전트, 교수자 기억·스킬 | 범위 밖 (CourseSpec을 만들고 읽는 쪽) |
| **CourseSpec** | LMS 중립 설계서 + 린트 + 퍼블리셔(계획 생성) | **여기** |
| 실행·LMS | 계획 승인과 실행, LMS별 MCP·API | moodle-agent-mcp, 허브, Canvas |

설계 에이전트의 개념은 DeepTutor의 교수자 버전입니다. DeepTutor의 지식베이스는 교수자가 올린 교재·강의계획서·과거 과정이 되고, 한 세션 안의 모드 전환은 "조사 → 목표 설계 → 활동 구성 → 문항 생성 → 검토"의 흐름이 되며, 학습자 프로필은 교수자의 교수 스타일과 지난 학기의 교훈이 됩니다. 그 모든 작업의 산출물이 CourseSpec입니다.

## 원칙

1. **설계서에는 학생이 없다.** 학생 이름, 성적, 제출물은 CourseSpec에 들어오지 않습니다. 운영 데이터가 다음 학기 개정에 쓰일 때도 가명처리된 집계로만 돌아옵니다.
2. **날짜는 상대적이다.** `due_day: 14`처럼 시작일 기준 일수로 적어 학기마다 재사용합니다.
3. **id는 영구적이다.** 설계서 id와 활동 id는 배포된 활동의 ID number(`cs:<설계서>:<활동>`)에 심어 재배포 때 같은 활동을 찾는 열쇠가 됩니다. 제목은 바꿔도 되지만 id는 바꾸지 않습니다.
4. **공통 코어 + 확장.** 모든 LMS가 지원하는 다섯 유형(page, file, assignment, quiz, discussion)이 코어이고, 나머지는 LMS에 따라 변환되거나 빠집니다. 퍼블리셔는 그 결과를 *변환 보고서*로 숨김없이 보여 줍니다.
5. **계획 후 승인 후 실행.** 퍼블리셔는 호출하지 않고 계획만 만듭니다. 교수자가 계획 전체와 변환 보고서를 보고 승인한 뒤에만 실행됩니다. moodle-agent-mcp의 `confirm=false` 미리보기를 강좌 단위로 묶은 것입니다.
6. **설계 품질은 배포 전에.** 학습목표–활동–평가의 정렬, 학습 부담, 선수조건 순환은 LMS에 올라간 뒤에는 보기 어렵습니다. 린트가 그 자리입니다.

## 하지 않는 것

- **또 하나의 LMS가 되지 않습니다.** 수강, 진도, 채점, 학생 소통은 LMS의 일입니다. 워크스페이스는 설계와 콘텐츠 생성까지만 합니다.
- **LMS 편집기를 다시 만들지 않습니다.** 세부 서식이나 LMS 고유 기능은 `extensions`로 넘기거나 배포 후 LMS에서 다룹니다.
- **처음부터 양방향 동기화를 하지 않습니다.** v0.x는 워크스페이스 → LMS 단방향이며, LMS에서 직접 바뀐 내용은 드리프트로 *감지*만 합니다 (로드맵).

## 이름에 대하여

Canvas에는 마스터 강좌를 여러 강좌로 동기화하는 "Blueprint Courses" 기능이 있습니다. 혼동을 피하려고 이 설계서는 "블루프린트"가 아니라 **CourseSpec(과정 설계서)**이라고 부릅니다.
